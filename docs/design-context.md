# 전단지(Flyer.G) 디자인 컨텍스트

> **이 문서는 화면 배치를 규정하지 않는다.**
> 무엇을 위한 화면인지, 어떤 정보와 판단이 오가는지, 무엇을 어기면 제품이 망가지는지만 적는다.
> 배치, 정보 구성, 시각적 표현은 디자이너의 판단에 맡긴다.
>
> 여기 적힌 것 중 **"절대 조건"** 절만 협상 불가다. 나머지는 더 나은 안이 있으면 바꾼다.

## 1. 이 제품이 무엇인가

**GIST 학사 기숙사의 종이 게시판을 디지털 사이니지로 바꾸는 시스템이다.**

기숙사 로비의 65인치 TV 2대에 승인된 포스터가 자동으로 돌아가고, 관리자 웹에서 신청과
승인을 처리한다. 게시 기간이 끝나면 자동으로 내려간다.

### 왜 필요한가

학기 초가 되면 동아리 모집, 행사 안내 포스터가 게시판을 뒤덮어 아무것도 읽히지 않는다.
게시하려면 `출력 → 하우스 오피스 아워 방문 → 승인 스티커 수령 → 직접 부착 → 직접 제거`를
거쳐야 한다. 기간이 지난 포스터는 아무도 떼지 않아 계속 붙어 있다.

### 어디에 붙는가

GIST 통합 공지 플랫폼 **Ziggle**(`https://ziggle.gistory.me`)의 연장이다. 별도 서비스가
아니라, Ziggle에 공지를 쓰는 흐름 안에서 "디지털 게시판에도 게시" 옵션을 켜는 형태다.
TV의 QR을 찍으면 Ziggle 원문으로 간다.

**디자인 함의**: 사용자는 이미 Ziggle을 쓰던 사람이다. 완전히 새로운 서비스를 배우는
느낌이 아니라 익숙한 흐름의 연장처럼 느껴져야 한다.

## 2. 사용자와 그들이 하려는 일

### 게시자 — 동아리·학생회·학과·교내 조직

- **누구**: 동아리 홍보 담당 학생이 대부분. 디자인·행정 전문가가 아니다.
- **언제**: 학기 초, 행사 2~3주 전. 몰아서 한 번 쓰고 한동안 안 쓴다.
- **기기**: 노트북 또는 휴대폰
- **하려는 일**: 만들어둔 포스터를 올리고, 언제부터 언제까지 띄울지 정해 신청한다.
- **알고 싶은 것**: 내 신청이 지금 어느 단계인가. 반려됐다면 **왜**, 그리고 **뭘 고쳐야** 하나.
- **실패**: 신청해놓고 몇 주 뒤에야 반려된 걸 알게 되는 것. 반려 사유가 "부적합"처럼
  모호해서 뭘 고칠지 모르는 것.

### 하우스 관리자 — 검토·승인 담당

- **누구**: 기숙사 운영 담당 교직원 또는 조교
- **언제**: 하루 한두 번, 짧게. 학기 초에는 한 번에 20건 넘게 몰린다.
- **기기**: 데스크톱
- **하려는 일**: 대기 목록을 훑고 승인/반려를 결정한다. 문제가 생긴 게시물을 즉시 내린다.
- **판단 근거**: 포스터가 TV에서 읽히는가, Ziggle 원문과 내용이 맞는가, 기간이 적절한가,
  중복이 아닌가, 부적절한 내용이 없는가
- **실패**: 한 건 판단하는 데 화면을 여러 번 오가야 하는 것. 다른 관리자가 이미 처리한
  건을 모르고 또 처리하는 것.

### 시스템 운영자 — P1 이후

기기 등록, 관리자 권한 부여, 장애 대응, 감사 로그 조회. MVP에서는 하우스 관리자와 같은
사람일 수 있지만 권한은 분리한다.

### 시청자 — TV 앞의 학생

- **상황**: 기숙사 로비를 **지나가면서**, 2~5m 거리에서, 몇 초 본다. 로그인하지 않는다.
- **하려는 일**: 뭐가 걸려 있는지 훑고, 관심 있으면 QR을 찍는다.
- **실패**: 멀어서 제목이 안 읽히는 것. QR이 너무 작아서 안 찍히는 것. 지나간 행사가
  아직 걸려 있는 것.

### 디스플레이 기기 — 사용자가 아님

라즈베리파이가 기기 전용 자격 증명으로 편성을 받아 재생만 한다. 사람이 조작하지 않는다.
**TV 화면에는 조작 UI가 없어야 한다.**

## 3. 핵심 흐름

### 3.1 게시 신청

```
Ziggle 공지 작성 → "디지털 게시판에도 게시" 켜기 → 포스터 업로드
→ 게시 기간·정보 입력 → TV에서 어떻게 보일지 확인 → 제출
```

이 흐름에서 게시자가 확신을 얻어야 하는 것:

- 내가 올린 이미지가 TV에서 잘리거나 뭉개지지 않는다
- 언제부터 언제까지 걸리는지 내가 정확히 이해했다
- 지금 제출하면 바로 걸리는 게 아니라 **승인을 기다린다**

### 3.2 검토·승인

```
대기 목록 → 상세 검토(포스터 원본 + TV 미리보기 + Ziggle 원문)
→ 승인 | 사유를 적어 반려
```

승인하면 시작 시각에 따라 `예약됨` 또는 `게시 중`이 된다. 관리자는 결정 전에
**대상 위치·기간·검토 중인 버전**을 마지막으로 확인해야 한다.

### 3.3 자동 게시·종료

기기가 주기적으로 편성을 받아 재생한다. 종료 시각이 지나면 다음 동기화 주기 안에
사라진다. **사람이 개입하지 않는다.**

### 3.4 반려 후 재신청

게시자가 사유를 보고 → 포스터나 정보를 고쳐 → 재신청.
이전 이력은 남고 새 검토 회차가 생긴다. 관리자는 **뭐가 바뀌었는지** 알 수 있어야 한다.

### 3.5 긴급 중단

게시 중인 콘텐츠에 문제가 생겼을 때 관리자가 사유를 적고 즉시 내린다.
모든 기기에서 다음 동기화 안에 사라지고, 누가 언제 왜 내렸는지 기록된다.

## 4. 상태 — 디자인이 표현해야 하는 핵심

신청은 10개 상태를 가진다. **이 상태를 얼마나 명확히 전달하느냐가 이 제품 UI의 본질이다.**

| 상태 | 게시자에게 | 관리자에게 | 여기서 할 수 있는 일 |
|---|---|---|---|
| **작성 중** | 아직 안 냈다 | 안 보임 | 이어 쓰기, 제출, 삭제 |
| **승인 대기** | 기다리는 중 | **지금 처리할 것** | (게시자) 취소 / (관리자) 승인·반려 |
| **반려됨** | **내가 고쳐야 한다** | 처리 완료 | 사유 확인, 수정 후 재신청, 취소 |
| **승인됨** | 통과했다 | 편성 계산 중 | 중단 |
| **예약됨** | 곧 걸린다 | 예정된 것 | 취소, 중단 |
| **게시 중** | 지금 TV에 있다 | 노출 중 | 중단 |
| **종료됨** | 끝났다 | 지난 것 | 보관 |
| **게시 중단** | **관리자가 내렸다** | 내가 내린 것 | 사유 확인, 재검토 요청 |
| **신청 취소** | 내가 취소했다 | 취소된 것 | 없음 |
| **보관됨** | 안 보임 | 목록에서 숨김 | 없음 |

### 상태에 대해 알아야 할 것

1. **상태는 시간이 지나면 저절로 바뀐다.** 승인된 건은 시작 시각이 되면 `예약됨` →
   `게시 중`, 종료 시각이 되면 `종료됨`이 된다. 사용자가 아무것도 안 해도 화면의 값이
   달라진다.
2. **주의가 필요한 상태와 그렇지 않은 상태의 무게가 다르다.** `승인 대기`(관리자가
   행동해야 함), `반려됨`·`게시 중단`(게시자가 행동해야 함)은 나머지와 다르게 읽혀야
   한다.
3. **색만으로 구분하면 안 된다.** 문구를 항상 함께 쓴다. (접근성 필수 조건)
4. 관리자 화면은 **20건 넘는 목록에서 상태를 훑는** 상황이 기본이다.

## 5. 필요한 화면

배치는 정하지 않는다. 각 화면이 **어떤 문제를 푸는지**와 **없으면 안 되는 정보**만 적는다.
하나의 화면으로 합치거나 쪼개는 것도 디자이너 판단이다.

### 5.1 대시보드 — 지금 뭐가 어떤 상태인가

- **푸는 문제**: 로그인하고 처음 봤을 때 "내가 할 일이 있나?"를 몇 초 안에 알기
- **필요한 것**: 상태별 건수, 그 수치의 **기준 시각**, 내 콘텐츠 목록, (관리자에게는)
  승인 대기 목록
- **역할에 따라 다름**: 게시자는 내 신청만, 관리자는 전체 + 대기 건
- **금지**: 근거 없는 증감률, 의미가 불분명한 "조회수". 노출 통계는 수집 API가 확정되기
  전까지 만들지 않는다

### 5.2 게시 신청 — 포스터를 올리고 기간을 정한다

- **푸는 문제**: 처음 쓰는 사람이 헤매지 않고 유효한 신청을 만들기
- **필요한 것**: 이미지 업로드, 제목·카테고리·기간·Ziggle 링크 입력, **TV에서 어떻게
  보이는지 미리보기**, 제출
- **어려운 지점**:
  - 업로드 제약(형식·용량·해상도)을 **올리기 전에** 알려줘야 한다
  - 잘못된 입력을 제출 버튼 누른 뒤에 알려주면 늦다
  - 미리보기는 단일 화면과 4분할 두 가지 모두 확인할 수 있어야 한다 (같은 포스터가
    4분할에서는 작게 나온다)
  - 업로드가 실패해도 입력한 다른 값이 날아가면 안 된다

### 5.3 신청 상세 — 이 건이 어떻게 됐나

- **푸는 문제**: 상태·이력·사유를 한자리에서 확인하고, 지금 가능한 작업을 하기
- **필요한 것**: 포스터, Ziggle 원문 링크, 게시 기간, 현재 상태, **검토 이력
  타임라인**(누가 언제 승인/반려했고 사유가 무엇인지), 권한과 상태에 맞는 작업 버튼
- **어려운 지점**: 같은 화면을 게시자와 관리자가 보는데 할 수 있는 일이 다르다

### 5.4 승인 대기 목록 — 오늘 처리할 것

- **푸는 문제**: 여러 건을 빠르게 훑고 우선순위를 정하기
- **필요한 것**: 썸네일, 제목, 게시자·조직, 요청 기간, 제출 시각, 필터
- **어려운 지점**: 학기 초에 20건 넘게 쌓인다. 스크롤이 길어지는 것을 전제로 설계한다

### 5.5 검토 상세 — 승인할지 결정한다

- **푸는 문제**: 결정에 필요한 근거를 한 화면에 모으기
- **필요한 것**: **포스터 원본**(원래 화질 확인용)과 **TV 미리보기**(실제 노출 모습) 둘 다,
  Ziggle 원문(새 창), 기간·대상, 해상도·비율 경고, 검토 중인 버전 번호
- **결정 절차**: 승인은 확인 단계를 거친다. 반려는 **사유 입력이 필수**이고 게시자에게
  그대로 보인다
- **어려운 지점**:
  - 다른 관리자가 이미 처리했을 수 있다 → 성공한 척하면 안 되고, 최신 상태를 다시
    불러오게 안내해야 한다
  - 반려 사유가 게시자에게 **행동 가능한 정보**여야 한다 (분류 + 구체 설명)

### 5.6 TV 플레이어 — 시청자가 보는 화면

같은 렌더링이 게시 신청 미리보기에서도 재사용된다.

- **단일 레이아웃**: 포스터 1장 + 제목·카테고리·일시·장소·주최·QR
- **4분할 레이아웃**: 한 번에 최대 4장
- **빈 상태**: 걸 콘텐츠가 없을 때. 검은 화면 대신 브랜드·현재 시각·안내 문구
- **오류/오프라인**: 안전한 대체 화면. **내부 오류 메시지나 토큰을 절대 노출하지 않는다**
- **필수**: QR 옆에 "Ziggle에서 자세히 보기" 같은 목적 문구. 제목이 길 때 안전하게 잘리기
- **금지**: 레이아웃 전환 버튼, 페이지 인디케이터, 일시정지 버튼 — 운영 화면에서는 전부
  숨긴다. 관리자 미리보기 모드에서만 보인다

### 5.7 나머지

- **로그인** — Ziggle 계정 연동. 비로그인 상태로 관리 화면에 접근하면 여기로 오고,
  로그인 후 원래 가려던 곳으로 돌아간다
- **기기 관리** (P1) — 위치별 기기 목록, 온라인/오프라인, 마지막 통신 시각
- **감사 로그** (운영자) — 누가 언제 무엇을 했는지
- **없는 화면 / 권한 없음** — 삭제됐거나 접근할 수 없는 건

## 6. 콘텐츠의 실제 모습

디자인은 이 데이터를 견뎌야 한다.

### 포스터

- **세로 3:4** 또는 A계열 세로형. 가로 포스터는 들어오지 않는다고 가정한다
- 학생이 직접 만든 것이라 **품질 편차가 크다.** 글자가 빽빽한 것, 저해상도, 여백 없는 것
- 형식 JPEG·PNG·WebP, 최대 10MB, 짧은 변 1080px 이상 권장
- **현재 목 데이터에는 실제 포스터 이미지가 없다.** 모두 대체 화면으로 그려진다

### 제목 — 실제 샘플

```
오픈 동방                        13자
MACMOO 정기공연                  19자
수리 전공 설명회                  23자
지구는 처음이야 동아리 부스        39자
인포팀 OTL 앱 출시 이벤트         34자
```

최대 80자까지 허용된다. **한국어라 줄바꿈이 단어 단위로 되지 않는다**(`break-keep` 필요).
가장 긴 경우를 가정한 예시:

```
2026학년도 1학기 기숙사 디지털 게시판 게시 신청 안내 및 승인 절차 변경 공지
```

### 그 밖의 필드

| 필드 | 예시 | 특성 |
|---|---|---|
| 부제 | "수리과학부 전공 탐색 세션" | 없을 수 있음 |
| 카테고리 | 공지 / 동아리 / 공연 / 행사 / 학과 | 5종. 장기적으로 Ziggle 분류를 따름 |
| 주최 | "GIST 수리과학부", "총학생회 이벤트팀" | 조직명. 개인 이름일 수도 있음 |
| 장소 | "대학 A동 115호", "학사 기숙사 일대", "온라인" | 없을 수 있음 |
| 기간 | 2026.08.15 ~ 2026.08.29 | 최대 14일. 종료 없는 게시는 금지 |
| 상세 링크 | `https://ziggle.gistory.me/notices/...` | QR의 유일한 원천 |

### 규모

- 평상시 한 자리(기숙사)에 게시 중 3~10건
- **학기 초 급증**: 승인 대기 20건 이상, 전체 50건 이상
- 디스플레이 2대로 시작, 확장 예정

## 7. 절대 조건

여기만 협상 불가다.

### TV 화면

| | |
|---|---|
| 해상도 | **1920×1080 가로 고정** |
| 화면 | 65인치 비즈니스 TV |
| 시청 거리 | **2~5m — 지나가면서 몇 초** |
| 기기 | Raspberry Pi 4B, Chromium kiosk 모드 |
| 성능 | 30fps 이상 유지. **상시 애니메이션 금지** |
| 조작 | **없음.** 터치도 마우스도 없다 |

- 텍스트와 QR은 **5m 밖에서 판별 가능**해야 한다
- QR은 스캔 가능한 크기와 여백(quiet zone), 충분한 대비를 가져야 한다
- 깜빡임, 급격한 전환, 과도한 모션 금지
- 화면에 디버그 정보·토큰·내부 오류를 절대 노출하지 않는다

### 시간

- 저장·통신은 **UTC**, 표시는 **Asia/Seoul** 고정
- 게시 여부 판정은 **서버 시각** 기준. 기기 시계를 믿지 않는다

### 접근성 (관리자 웹)

- 키보드만으로 전체 흐름이 가능해야 한다
- 포커스가 어디 있는지 항상 보여야 한다
- **색만으로 상태·카테고리를 구분하지 않는다.** 문구를 함께 쓴다
- 모든 이미지에 대체 텍스트
- 폼의 label·설명·오류가 입력에 연결되어야 한다
- 사용자의 모션 감소 설정을 존중한다
- 본문 대비 4.5:1 이상

### 정직성

- **없는 데이터를 지어내지 않는다.** 증감률, 조회수, 인기도 같은 지표는 수집 근거가
  생기기 전까지 만들지 않는다
- 서버에 반영되지 않는 버튼을 두지 않는다. 눌러서 화면만 바뀌고 새로고침하면 돌아오는
  동작은 사용자를 속이는 것이다
- "조회수"는 사람이 본 횟수가 아니라 **기기가 정상 렌더링한 횟수**다. 도입한다면 이름을
  그렇게 붙인다

### 개인정보

- TV에는 승인된 공개 정보만. 게시자 개인 연락처를 임의로 노출하지 않는다
- 얼굴·음성·Wi-Fi 식별자를 수집하지 않는다

## 8. 놓치기 쉬운 상태

실제 운영에서 자주 나타나는데 시안에서 빠지기 쉬운 것들이다. 각각 어떻게 보일지 정해야
한다.

| 상황 | 언제 |
|---|---|
| **로딩** | 첫 진입, 목록 갱신 |
| **비어 있음** | 신청이 하나도 없는 신규 사용자, 승인 대기 0건, TV에 걸 게 없음 |
| **오류** | 네트워크 끊김, 서버 오류. 요청 ID를 함께 보여주되 내부 정보는 감춘다 |
| **권한 없음** | 게시자가 관리자 화면에 접근 |
| **없는 항목** | 삭제되었거나 접근할 수 없는 신청 |
| **깨진 이미지** | 포스터를 불러오지 못함. 목록에서, TV에서 각각 |
| **아주 긴 한국어** | 80자 제목, 긴 조직명, 긴 반려 사유 |
| **처리 중** | 제출·승인이 서버 응답을 기다리는 동안. 중복 클릭 차단 |
| **동시 처리 충돌** | 다른 관리자가 먼저 처리함. 성공으로 보이면 안 된다 |
| **오프라인** | TV가 네트워크를 잃음. 마지막 유효 편성을 계속 재생 |
| **좁은 화면** | 관리자 웹 최소 지원 폭 320px |

## 9. 지금 구현된 것 — 어디까지 바꿔도 되나

프로토타입이 동작 중이다. `bun run dev` 후 `/`(대시보드), `/studio`(신청), `/display`(TV),
`/catalog`(컴포넌트 카탈로그).

### 바꿔도 되는 것 — 전부

화면 배치, 정보 구성, 색, 타이포, 컴포넌트 형태 모두 열려 있다. 지금 구현은 기능을
확인하기 위한 것이지 디자인 결정이 아니다.

### 바꿀 때 비용이 드는 것

| | 현재 | 비고 |
|---|---|---|
| 서체 | Pretendard 가변, 자기 호스팅 | 한국어 웹에서 가장 무난. 바꾸려면 라이선스와 TV 렌더링 확인 필요 |
| 브랜드 색 | 보라 계열 + 로고의 주황 `G` | 기존 프로토타입에서 이어짐. 확정된 CI는 아님 |
| 컴포넌트 기반 | shadcn/ui (Radix) | 접근성 동작(포커스 트랩, 키보드)이 여기서 나온다. 갈아엎으면 다시 만들어야 함 |
| 토큰 구조 | CSS 변수 단일 원천 | 값은 자유롭게. 체계를 없애면 화면마다 값이 흩어진다 |

자세한 내용은 [design-system.md](./design-system.md).

### 아직 자리표시자인 것

- **포스터 이미지** — 실제 이미지가 없어 전부 대체 화면. `public/posters/`에 넣으면 대체됨
- **QR** — 스캔되지 않는 패턴. 실제 QR 생성은 미구현
- **사용자 이름·역할** — 인증 연동 전이라 고정값

## 10. 범위 밖

MVP에서 하지 않는 것. 디자인에 넣지 않아도 된다.

- 포스터를 만들어주는 디자인 편집기 (템플릿, 요소, 다중 페이지) — 완성된 포스터를
  올리는 것까지가 이 제품이다
- TV 터치 상호작용
- 영상, 축하 메시지, 날씨 위젯 (P2)
- 개인 맞춤 추천, 행동 추적
- 광고·결제
- 다크 테마
- 다단계 승인, 조직별 승인자

## 11. 아직 정해지지 않은 것

디자인 판단에 영향을 주는 미결정 사항이다. 답이 나오기 전까지는 **양쪽 다 가능한 안**을
잡거나, 가정을 명시하고 진행한다.

1. 전단지는 Ziggle 안의 기능인가, 별도 도메인의 연결 서비스인가?
   → 전역 내비게이션과 브랜딩의 강도가 달라진다
2. 게시 신청은 Ziggle 공지 작성 중에만 가능한가, 기존 공지에서도 가능한가?
   → 신청 화면의 진입 지점이 달라진다
3. 개인도 신청할 수 있나, 승인된 조직만 가능한가?
   → 게시자 표기 방식이 달라진다
4. 위치별 기본 레이아웃은 단일인가 4분할인가?
5. 승인 후 원문이 수정되면 기존 게시를 유지하나, 즉시 중단하나?
6. 야간에 화면을 끄거나 밝기를 낮추나?
7. 포스터가 부족할 때 무엇을 대신 띄우나? (상시 안내, 사용법, 브랜드 화면)

## 12. 한 문장으로

**포스터를 붙이러 가는 대신 올리고, 스티커를 받는 대신 승인을 기다리고, 떼러 가는 대신
기다리면 내려가는 것.** 이 세 가지가 각 사용자에게 분명하게 느껴지면 성공이다.
