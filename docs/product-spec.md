# 전단지(Flyer.G) 제품 기획 및 기능 명세서

> 문서 상태: 검토용 초안  
> 버전: 0.1  
> 작성일: 2026-07-28  
> 기준 시간대: Asia/Seoul  
> 목적: 사람과 구현 AI Agent가 동일한 제품 범위, 규칙, 데이터 및 완료 조건을 이해하도록 한다.

## 0. 문서 사용법

- `확정`: 기존 수행계획서 또는 현재 기획에서 명시된 내용
- `제안`: 구현 가능성과 운영 안정성을 위해 이 문서에서 구체화한 내용
- `미결정`: 담당자 논의가 필요한 내용
- 기능 ID(`FR-*`)는 이슈, 커밋, API, 테스트 케이스에서 공통으로 사용한다.
- AI Agent는 구현 전에 해당 기능의 우선순위, 선행 조건, 인수 조건을 확인한다.
- 미결정 항목을 임의로 확정해 구현하지 않는다. 단, 프로토타입에서는 문서의 권장안을 기본값으로 사용할 수 있다.

## 1. 제품 개요

### 1.1 한 줄 설명

전단지는 GIST 통합 공지 플랫폼 Ziggle과 연동하여, 기숙사 내 포스터의 등록, 승인, 편성, 노출, 종료 과정을 자동화하는 웹 기반 디지털 게시판 시스템이다.

### 1.2 배경과 문제

현재 기숙사 게시판은 다음과 같은 문제를 가진다.

1. 학기 초 동아리 모집, 행사 안내 등의 포스터가 한꺼번에 몰려 가독성이 낮다.
2. 게시 절차가 `출력 → 하우스 오피스 아워 방문 → 승인 스티커 수령 → 직접 부착 → 직접 제거`로 이루어진다.
3. 게시자와 하우스 관리자 모두 반복적인 시간·물리 비용을 부담한다.
4. 게시 종료일이 지난 포스터가 방치될 수 있다.
5. 중요한 공지의 우선순위를 일관되게 표현하기 어렵다.
6. 물리적 게시물은 노출 여부와 운영 상태를 측정하기 어렵다.

### 1.3 해결 방식

1. Ziggle 공지 작성 흐름에서 디지털 게시판 게시를 함께 신청한다.
2. 하우스 관리자가 신청 콘텐츠를 검토하고 승인 또는 반려한다.
3. 승인된 콘텐츠를 설정된 기간과 우선순위에 따라 TV에 자동 노출한다.
4. 게시 종료 시 자동으로 화면에서 제거한다.
5. 여러 디스플레이의 상태와 편성을 중앙에서 관리한다.

### 1.4 제품명

- 공식명: 전단지
- 영문/코드명: Flyer.G
- 의미: 전단지의 디지털 전환과 GIST를 나타내는 이름

### 1.5 외부 서비스

- Ziggle 운영 주소: <https://ziggle.gistory.me>
- Ziggle 역할: GIST 내부 여러 공지사항을 통합해 제공하는 기존 공지 플랫폼
- 전단지 역할: Ziggle 공지 중 게시 신청과 승인을 거친 콘텐츠를 물리 공간의 디지털 사이니지에 노출
- 참고: 실제 API 주소, 인증 방식, 권한 모델은 Ziggle 팀과 확인 후 확정한다.

## 2. 목표와 성공 기준

### 2.1 제품 목표

| ID | 목표 | 측정 예시 |
|---|---|---|
| G-01 | 포스터 게시 절차의 디지털화 | 등록부터 종료까지 온라인 처리 비율 |
| G-02 | 하우스 운영 부담 감소 | 건당 승인·제거에 드는 평균 작업 시간 |
| G-03 | 정보 가독성과 적시성 향상 | 게시 기간 준수율, 화면 오류 시간 |
| G-04 | Ziggle 사용자 흐름 재사용 | Ziggle 공지 중 사이니지 신청 전환율 |
| G-05 | 학내 디지털 정보 인프라로 확장 | 운영 디스플레이 수, 지원 콘텐츠 유형 |

### 2.2 MVP 성공 기준 제안

- 승인된 콘텐츠의 95% 이상이 설정된 시작 시각부터 5분 이내에 디스플레이에 반영된다.
- 종료 시각이 지난 콘텐츠가 5분 이상 계속 노출되는 비율이 1% 미만이다.
- 정상 네트워크 환경에서 디스플레이 월 가동률이 99% 이상이다.
- 관리자 개입 없이 예약 시작과 종료가 수행된다.
- 승인, 반려, 게시 시작, 게시 종료 이력이 모두 감사 로그에 남는다.
- 네트워크가 일시 중단되어도 마지막 유효 편성을 계속 재생한다.

### 2.3 비목표

MVP에서는 다음을 목표로 하지 않는다.

- Ziggle을 대체하는 별도 공지 작성 플랫폼
- TV에서의 터치 상호작용
- 개인별 맞춤 추천 또는 행동 추적
- 광고 판매 및 결제
- 포스터를 자동 생성하는 전문 디자인 도구
- 모든 학교 건물로의 즉시 확장
- 실시간 방송 또는 영상 스트리밍

## 3. 사용자와 권한

### 3.1 사용자 역할

#### 게시자(Submitter)

- 대상: 동아리, 학생회, 학과, 학교 조직, GIST 구성원
- Ziggle에서 공지를 작성하고 사이니지 게시를 신청한다.
- 본인이 신청한 콘텐츠의 상태와 반려 사유를 확인한다.
- 허용된 상태에서 내용을 수정하거나 게시를 취소한다.

#### 하우스 관리자(Reviewer/Admin)

- 승인 대기 콘텐츠를 검토한다.
- 승인, 반려, 게시 중단, 우선순위 및 편성 설정을 수행한다.
- 디스플레이 상태와 전체 콘텐츠를 관리한다.
- 모든 관리 작업에는 행위자와 시각이 기록된다.

#### 시스템 운영자(Super Admin)

- 관리자 권한, 디스플레이 기기, 위치, 기본 정책을 관리한다.
- 장애 대응과 감사 로그 조회를 수행한다.
- MVP에서는 하우스 관리자와 동일 계정일 수 있으나 권한 개념은 분리한다.

#### 디스플레이 클라이언트(Device)

- 사용자 계정이 아닌 기기 전용 자격 증명으로 읽기 전용 편성을 가져온다.
- 승인·수정 API에 접근할 수 없다.
- 자신의 상태와 재생 정보를 서버에 보고한다.

#### 시청자(Viewer)

- 기숙사에서 TV를 보는 학생 및 방문자
- 로그인 없이 콘텐츠를 보고 QR 코드로 Ziggle 상세 공지에 접근한다.

## 4. 핵심 사용자 흐름

### 4.1 게시 신청

1. 게시자가 Ziggle 공지를 작성 또는 수정한다.
2. `디지털 게시판에도 게시` 옵션을 활성화한다.
3. 포스터 이미지와 게시 희망 기간 등 필수 정보를 입력한다.
4. TV 화면 미리보기를 확인한다.
5. Ziggle 공지와 사이니지 게시 신청을 제출한다.
6. 시스템은 신청을 `승인 대기`로 저장하고 관리자에게 알린다.
7. 게시자는 상태를 확인할 수 있다.

### 4.2 승인

1. 관리자가 승인 대기 목록을 연다.
2. 포스터, Ziggle 원문, 게시 기간, 대상 위치 및 화면 미리보기를 검토한다.
3. 관리자가 승인하거나 반려 사유를 입력해 반려한다.
4. 승인 건은 시작 시각에 따라 `예약됨` 또는 `게시 중` 상태가 된다.
5. 반려 건은 게시자에게 사유와 수정 방법이 전달된다.

### 4.3 자동 게시

1. 디스플레이는 자신의 위치에 유효한 편성을 주기적으로 동기화한다.
2. 현재 시각, 승인 상태, 대상 위치, 우선순위에 따라 재생 목록을 만든다.
3. 콘텐츠를 단일 또는 분할 레이아웃으로 순환 표시한다.
4. 종료 시각이 되면 다음 동기화 주기 내에 재생 목록에서 제거한다.
5. 네트워크 오류 시 마지막으로 검증된 편성을 재생한다.

### 4.4 반려 후 재신청

1. 게시자가 반려 사유를 확인한다.
2. 포스터 또는 메타데이터를 수정한다.
3. 재신청하면 기존 이력은 유지되고 새 검토 회차가 생성된다.
4. 관리자는 변경된 항목을 이전 버전과 비교할 수 있다.

### 4.5 긴급 게시 중단

1. 관리자가 게시 중 콘텐츠에서 `즉시 중단`을 선택한다.
2. 시스템은 사유 입력을 요구한다.
3. 콘텐츠는 모든 대상 기기의 유효 편성에서 제거된다.
4. 기기는 다음 동기화 시 제거하며, 작업은 감사 로그에 기록된다.

## 5. 범위와 우선순위

### 5.1 P0 - MVP 필수

- Ziggle 로그인 및 사용자 식별
- Ziggle 공지와 연결된 사이니지 게시 신청
- 이미지 포스터 업로드
- 제목, 게시 기간, 상세 링크, 카테고리 입력
- 미리보기
- 승인 대기 목록과 상세 검토
- 승인 및 사유가 포함된 반려
- 예약 시작과 자동 종료
- 단일 포스터 및 4분할 디스플레이
- 콘텐츠 자동 순환
- QR 코드로 Ziggle 원문 연결
- 기기별 읽기 전용 편성 조회
- 오프라인 캐시와 자동 복구
- 기본 감사 로그

### 5.2 P1 - 시범 운영 안정화

- 여러 디스플레이 및 위치별 편성
- 기기 온라인/오프라인 상태와 마지막 통신 시각
- 중요 콘텐츠 고정 또는 가중치 기반 우선 노출
- 게시자와 관리자 알림
- 콘텐츠 수정 및 재승인 정책
- 검색, 필터, 페이지네이션
- 노출 횟수 통계
- 원격 새로고침과 운영자 장애 화면

### 5.3 P2 - 확장

- 짧은 무음 영상
- 축하 메시지, 캠페인, 날씨 등 별도 콘텐츠 유형
- 조직별 승인자와 다단계 승인
- 템플릿 기반 콘텐츠 제작
- 전체 캠퍼스 디스플레이 그룹
- 시간대별 편성 및 이벤트 모드
- 고급 운영 분석

## 6. 콘텐츠 도메인

### 6.1 콘텐츠 유형

MVP의 기본 유형은 `POSTER` 하나로 제한한다.

| 유형 | 설명 | 우선순위 |
|---|---|---|
| POSTER | 세로형 이미지와 Ziggle 공지 링크 | P0 |
| VIDEO | 무음 또는 음소거 자동 재생 영상 | P2 |
| MESSAGE | 축하·안내용 텍스트 카드 | P2 |
| SYSTEM | 장애·점검·긴급 공지 | P1 |

### 6.2 카테고리

현재 UI의 초기 카테고리는 다음과 같다.

- 공지
- 동아리
- 공연
- 행사
- 학과

카테고리는 장기적으로 Ziggle 분류 체계를 단일 원천으로 사용해야 하며, 전단지에서 별도 문자열 목록을 중복 관리하지 않는 것을 권장한다.

### 6.3 상태 모델

#### 상태

| 내부 상태 | UI 표시 | 의미 |
|---|---|---|
| DRAFT | 작성 중 | 제출 전 임시 저장 |
| PENDING_REVIEW | 승인 대기 | 관리자 검토 대기 |
| REJECTED | 반려됨 | 사유 확인 후 수정·재신청 가능 |
| APPROVED | 승인됨 | 승인 완료, 편성 계산 전 |
| SCHEDULED | 예약됨 | 시작 시각 전 |
| PUBLISHED | 게시 중 | 현재 하나 이상의 기기에 노출 가능 |
| ENDED | 종료됨 | 종료 시각 도달 또는 정상 종료 |
| SUSPENDED | 게시 중단 | 관리자에 의해 즉시 중단 |
| CANCELED | 신청 취소 | 게시자가 시작 전에 취소 |
| ARCHIVED | 보관됨 | 운영 목록에서 숨긴 종료 데이터 |

#### 허용 전이

```text
DRAFT -> PENDING_REVIEW
PENDING_REVIEW -> APPROVED | REJECTED | CANCELED
REJECTED -> PENDING_REVIEW | CANCELED
APPROVED -> SCHEDULED | PUBLISHED | SUSPENDED
SCHEDULED -> PUBLISHED | SUSPENDED | CANCELED
PUBLISHED -> ENDED | SUSPENDED
ENDED -> ARCHIVED
SUSPENDED -> PENDING_REVIEW | APPROVED | ENDED
```

#### 상태 계산 규칙

- 상태 판정은 클라이언트 시계가 아니라 서버 시각을 기준으로 한다.
- 저장 시각은 UTC, 입력과 표시는 `Asia/Seoul`을 사용한다.
- 승인 시 `startAt <= now < endAt`이면 `PUBLISHED`, `now < startAt`이면 `SCHEDULED`이다.
- `now >= endAt`이면 승인 여부와 관계없이 디스플레이에 포함하지 않는다.
- 상태 문자열만 믿지 않고 승인 여부와 기간 조건을 함께 검증한다.

## 7. 기능 요구사항

### 7.1 인증 및 Ziggle 연동

#### FR-AUTH-01 Ziggle 사용자 인증

- 우선순위: P0
- 게시자와 관리자는 Ziggle 또는 인포팀 통합 계정으로 로그인한다.
- 전단지는 비밀번호를 직접 저장하지 않는다.
- 권장 방식: Ziggle과 동일한 인증 제공자의 OAuth 2.0/OIDC 또는 Ziggle 세션 연동
- 인수 조건:
  - 비로그인 사용자가 관리 화면 접근 시 로그인으로 이동한다.
  - 로그인 후 원래 경로로 복귀한다.
  - 만료 토큰은 갱신하거나 재로그인을 요구한다.
  - 서버가 모든 변경 요청에서 권한을 다시 검증한다.

#### FR-INT-01 Ziggle 공지와 게시 신청 연결

- 우선순위: P0
- 하나의 신청은 반드시 하나의 Ziggle 공지 원문을 참조한다.
- Ziggle 공지 작성 화면에 `디지털 게시판에도 게시` 옵션을 제공한다.
- Ziggle 공지 ID, 제목, 작성자/조직, 카테고리, 상세 URL은 가능한 범위에서 자동 입력한다.
- 권장 모델: Ziggle `Notice`에 사이니지 필드를 직접 늘리기보다 별도 `SignageSubmission` 리소스를 연결한다.
- 인수 조건:
  - 존재하지 않거나 접근 권한이 없는 공지로 신청할 수 없다.
  - QR 링크는 해당 Ziggle 공지의 공식 HTTPS 주소다.
  - 공지 삭제·비공개 전환 시 연결된 게시를 즉시 중단하거나 관리자 확인 대상으로 전환한다.

#### FR-INT-02 동기화 정책

- 우선순위: P0
- 제목·공개 상태·상세 URL 등 원문 필드와 포스터 승인 대상 필드를 구분한다.
- 승인 후 포스터 이미지, 게시 기간 또는 제목이 바뀌면 재승인이 필요한 것을 기본 정책으로 한다.
- 사소한 본문 오탈자 수정은 재승인 없이 허용할 수 있다.
- 어떤 변경이 재승인을 유발하는지는 서버 정책으로 관리한다.

### 7.2 게시 신청 및 업로드

#### FR-SUB-01 이미지 업로드

- 우선순위: P0
- 지원 형식 제안: JPEG, PNG, WebP
- 최대 크기 제안: 파일당 10MB
- 최소 해상도 제안: 짧은 변 1080px
- 권장 비율: 세로 3:4 또는 A계열 세로형
- EXIF 위치 정보는 제거한다.
- 서버가 MIME, 확장자, 실제 파일 시그니처를 검증한다.
- SVG와 실행 가능한 파일은 MVP에서 받지 않는다.
- 인수 조건:
  - 잘못된 형식·크기·해상도는 업로드 전에 명확한 오류를 표시한다.
  - 업로드 성공 후 실제 TV 프레임에 맞춘 미리보기를 표시한다.
  - 실패 시 다른 입력값을 잃지 않고 재시도할 수 있다.

#### FR-SUB-02 게시 정보 입력

- 우선순위: P0
- 필수: 제목, 카테고리, 시작 시각, 종료 시각, 포스터, Ziggle 상세 링크
- 선택: 대상 위치, 게시자 메모
- 검증:
  - 제목은 공백 제거 후 1~80자
  - `endAt > startAt`
  - 과거 종료 시각 금지
  - 상세 링크는 허용된 Ziggle 도메인의 HTTPS URL
  - 최대 게시 기간은 운영 정책에 따라 제한

#### FR-SUB-03 화면 미리보기

- 우선순위: P0
- 단일 포스터와 4분할 레이아웃에서 결과를 확인한다.
- 이미지 잘림, 여백, 제목, 카테고리, QR 위치를 실제 디스플레이와 동일한 렌더링 컴포넌트로 표현한다.
- 미리보기 전용 구현과 플레이어 구현의 스타일 분기를 최소화한다.

#### FR-SUB-04 제출 및 중복 방지

- 우선순위: P0
- 제출 성공 시 신청 ID와 현재 상태를 표시한다.
- 더블 클릭이나 네트워크 재시도로 중복 생성되지 않도록 idempotency key를 사용한다.
- 제출 도중 페이지를 이탈하면 경고하거나 임시 저장한다.

#### FR-SUB-05 내 콘텐츠

- 우선순위: P0
- 게시자는 본인 또는 소속 조직의 신청 목록을 상태별로 조회한다.
- 각 항목에서 상태, 기간, 반려 사유, 대상 위치를 확인한다.
- P1에서 검색, 정렬, 페이지네이션을 추가한다.

### 7.3 검토 및 승인

#### FR-REV-01 승인 대기 목록

- 우선순위: P0
- 관리자는 최신 제출 순으로 승인 대기 건을 확인한다.
- 목록에는 썸네일, 제목, 게시자/조직, 요청 기간, 제출 시각, 긴급 여부를 표시한다.
- 상태, 날짜, 조직, 카테고리 필터를 제공한다.
- 두 관리자가 동시에 처리할 때 이미 처리된 건을 중복 승인하지 않는다.

#### FR-REV-02 상세 검토

- 우선순위: P0
- 포스터 원본과 화면 미리보기를 모두 제공한다.
- Ziggle 공지 원문을 새 창에서 확인할 수 있다.
- 게시 기간 충돌, 비율 미준수, 링크 오류를 경고한다.
- 현재 버전과 검토 대상 버전을 명확히 표시한다.

#### FR-REV-03 승인

- 우선순위: P0
- 승인 직전 대상 위치, 기간, 우선순위를 최종 확인한다.
- 승인한 버전의 미디어 체크섬을 고정한다.
- 승인 후 시작 시각에 따라 예약 또는 게시 중 상태로 전환한다.
- 게시자에게 결과를 알린다.

#### FR-REV-04 반려

- 우선순위: P0
- 반려 시 게시자에게 공개되는 사유 입력을 필수로 한다.
- 반려 분류 제안: 저해상도, 비율 문제, 정보 불일치, 부적절한 내용, 기간 문제, 중복, 기타
- 게시자는 기존 데이터를 복사해 수정·재신청할 수 있다.

#### FR-REV-05 게시 중단

- 우선순위: P0
- 관리자는 예약 또는 게시 중 콘텐츠를 즉시 중단할 수 있다.
- 중단 사유는 필수이며 게시자에게 표시한다.
- 모든 대상 기기에서 다음 동기화 주기 내 제거되어야 한다.

### 7.4 편성 및 디스플레이

#### FR-PLY-01 유효 재생 목록

- 우선순위: P0
- 다음 조건을 모두 만족한 콘텐츠만 포함한다.
  - 승인된 최신 버전
  - `startAt <= serverNow < endAt`
  - 중단·취소·삭제되지 않음
  - 해당 기기 또는 그룹이 대상에 포함됨
  - 미디어 검증 완료
- 응답에 서버 시각, 편성 버전, 캐시 만료 시각을 포함한다.

#### FR-PLY-02 레이아웃

- 우선순위: P0
- 지원 레이아웃:
  - `SINGLE`: 한 번에 포스터 1개
  - `FOUR_GRID`: 한 번에 포스터 최대 4개
- 콘텐츠 수가 슬롯보다 적을 때 빈 슬롯을 억지로 복제하지 않고 브랜드/안내용 fallback으로 채운다.
- 관리자 조작용 레이아웃 전환 버튼은 실제 키오스크 화면에서 숨긴다.
- 레이아웃은 기기 또는 그룹 설정으로 결정한다.

#### FR-PLY-03 자동 순환

- 우선순위: P0
- 기본 전환 간격 제안: 10초
- 설정 범위 제안: 5~60초
- 4분할은 한 페이지 단위로 순환한다.
- CSS 전환은 성능 저하가 없고 화면 번쩍임을 최소화한다.
- 플레이어 새로고침 후 목록 첫 항목만 과도하게 노출되지 않도록 시작 인덱스를 조정할 수 있다.

#### FR-PLY-04 우선순위

- 우선순위: P1
- 기본 콘텐츠는 동일 가중치로 순환한다.
- 중요 콘텐츠는 가중치 증가 또는 지정 슬롯 고정 중 하나의 정책을 사용한다.
- 한 콘텐츠가 전체 노출의 과도한 비율을 차지하지 않도록 상한을 둔다.
- 긴급 공지는 운영자만 설정할 수 있고 자동 만료 시각이 필수다.

#### FR-PLY-05 QR 및 상세 정보

- 우선순위: P0
- QR 코드는 Ziggle 원문으로 연결한다.
- TV 시청 거리에서 스캔 가능한 크기와 대비를 유지한다.
- URL 문자열을 QR 이미지로 서버에 영구 저장하기보다 클라이언트 또는 이미지 처리 계층에서 생성할 수 있다.
- QR 아래에 `Ziggle에서 자세히 보기`와 같은 목적을 표시한다.

#### FR-PLY-06 빈 화면과 오류 화면

- 우선순위: P0
- 유효 콘텐츠가 없으면 검은 화면 대신 브랜드, 현재 시각, 안내 문구를 표시한다.
- 미디어 하나가 깨져도 전체 재생을 중단하지 않고 다음 콘텐츠로 넘어간다.
- 인증 실패, 편성 실패, 저장 공간 부족은 운영 서버에 보고한다.
- 디버그 정보나 토큰을 공개 화면에 노출하지 않는다.

#### FR-PLY-07 오프라인 동작

- 우선순위: P0
- 마지막으로 성공한 편성과 미디어를 로컬에 저장한다.
- 네트워크 단절 시 캐시된 편성을 계속 재생한다.
- 캐시에서도 종료 시각을 적용하여 만료 콘텐츠를 제거한다.
- 재연결 시 지수 백오프로 동기화를 재개한다.
- 캐시가 전혀 없으면 안전한 기본 화면을 표시한다.

#### FR-PLY-08 기기 상태 보고

- 우선순위: P1
- 기기는 주기적으로 heartbeat를 전송한다.
- 포함 정보: 기기 ID, 앱 버전, 현재 편성 버전, 마지막 렌더 성공, 저장 공간, 화면 해상도
- 개인정보, 화면 촬영 이미지, 사용자 행동 정보는 기본 수집하지 않는다.

### 7.5 대시보드와 통계

#### FR-DASH-01 운영 요약

- 우선순위: P0
- 전체 콘텐츠, 게시 중, 예약, 승인 대기, 종료 수를 표시한다.
- 통계의 기간과 기준 시각을 명시한다.
- 현재 UI의 `총 조회수`는 의미가 불명확하므로 MVP에서는 제거하거나 `추정 노출 횟수`로 이름을 바꾼다.

#### FR-DASH-02 콘텐츠 목록

- 우선순위: P0
- 상태별 필터와 썸네일 목록을 제공한다.
- 항목 선택 시 상세, 수정, 취소, 중단 등 권한에 맞는 작업을 제공한다.
- 전체 데이터가 4개를 넘을 때도 접근할 수 있도록 전체 보기 또는 페이지네이션이 필요하다.

#### FR-DASH-03 노출 통계

- 우선순위: P1
- `조회수`는 실제 사람이 본 횟수가 아니라 디스플레이가 콘텐츠를 정상 렌더링한 횟수로 정의한다.
- 기기, 콘텐츠, 날짜별 집계를 제공한다.
- 중복·재시작으로 인한 과다 집계를 줄이기 위해 재생 세션 ID를 사용한다.
- 실제 사람의 시청 여부를 추정하지 않는다.

### 7.6 알림과 감사

#### FR-NOTI-01 상태 알림

- 우선순위: P1
- 게시자 알림: 제출 완료, 승인, 반려, 게시 시작, 게시 종료, 강제 중단
- 관리자 알림: 신규 승인 요청, 기기 장기 오프라인
- 채널은 Ziggle 인앱 알림을 우선하고 이메일은 선택 사항으로 둔다.

#### FR-AUD-01 감사 로그

- 우선순위: P0
- 승인, 반려, 수정, 중단, 권한 변경, 기기 등록을 기록한다.
- 감사 로그는 일반 콘텐츠 삭제와 함께 삭제하지 않는다.
- 운영자만 전체 로그를 조회할 수 있다.

## 8. 개념 API 계약

> 실제 경로와 스키마는 Ziggle OpenAPI 및 백엔드 구조를 확인한 후 확정한다. 아래 계약은 프론트엔드·백엔드 병렬 개발을 위한 제품 수준 인터페이스다.

### 8.1 게시자/관리자 API

```text
POST   /signage/submissions
GET    /signage/submissions?owner=me&status=...
GET    /signage/submissions/{id}
PATCH  /signage/submissions/{id}
POST   /signage/submissions/{id}/submit
POST   /signage/submissions/{id}/cancel

GET    /signage/reviews?status=PENDING_REVIEW
POST   /signage/submissions/{id}/approve
POST   /signage/submissions/{id}/reject
POST   /signage/submissions/{id}/suspend

POST   /signage/assets/presign
POST   /signage/assets/{id}/complete
```

### 8.4 공통 API 규칙

- JSON 필드는 코드에서 영어 `camelCase`를 사용한다.
- 날짜·시각은 ISO 8601 UTC로 전달한다.
- 목록 API는 cursor pagination을 권장한다.
- 변경 API는 인증, 권한 검증, 입력 검증, 감사 로그를 서버에서 처리한다.
- 오류 응답은 안정적인 `code`, 사용자용 `message`, 추적용 `requestId`를 포함한다.
- 업로드와 제출은 idempotency를 지원한다.
- 플레이리스트는 ETag 또는 버전 기반 조건부 요청을 지원한다.

## 9. 비기능 요구사항

### 9.1 하드웨어 및 실행 환경

- 초기 대상: 65인치 비즈니스 TV 2대
- 플레이어: Raspberry Pi 4B 4GB 2대
- 연결: HDMI, 유선 네트워크 우선
- 화면: 가로 16:9, 기준 1920x1080
- 브라우저: Chromium kiosk 모드
- 전원 복구 후 자동 부팅, 자동 로그인, 플레이어 자동 실행

### 9.2 성능

- 초기 플레이어 화면 표시: 캐시 존재 시 5초 이내
- 편성 API 응답: p95 500ms 이하 목표
- 승인·중단 반영: 정상 네트워크에서 5분 이내, 목표 1분
- 이미지 파생본은 화면 크기에 맞게 최적화하고 원본을 매번 내려받지 않는다.
- 애니메이션은 Raspberry Pi에서 끊김 없는 30fps 이상을 목표로 한다.

### 9.3 신뢰성

- 플레이어 프로세스 비정상 종료 시 자동 재시작
- API와 정적 미디어 장애를 분리하여 미디어 일부 오류가 전체 화면 장애로 이어지지 않게 한다.
- 서버 배포 중에도 마지막 유효 편성을 재생한다.
- 편성 응답과 미디어 체크섬을 검증한다.

### 9.4 보안

- 모든 통신은 HTTPS를 사용한다.
- 기기 토큰은 기기별 발급·폐기하며 브라우저 번들에 공용 관리자 키를 넣지 않는다.
- 관리자 권한은 서버에서 검증한다.
- 업로드 파일은 악성 파일 검사와 콘텐츠 타입 검증을 거친다.
- 저장소는 최소 권한을 적용하고 짧은 수명의 서명 URL 또는 CDN을 사용한다.
- QR 링크는 허용 도메인 검증으로 피싱 링크를 방지한다.
- 로그에 액세스 토큰, 세션, 개인정보를 기록하지 않는다.

### 9.5 개인정보

- TV 화면에는 게시 목적상 승인된 공개 정보만 표시한다.
- 게시자 개인 연락처를 포스터 외 메타데이터로 임의 노출하지 않는다.
- 노출 통계는 기기 이벤트 기반이며 얼굴·음성·Wi-Fi 식별자를 수집하지 않는다.
- 보관 기간과 삭제 정책은 GIST 및 Ziggle 정책에 맞춘다.

### 9.6 접근성과 가독성

- TV UI는 먼 거리에서 읽을 수 있는 크기와 명암 대비를 사용한다.
- QR 외에도 콘텐츠 제목과 목적을 텍스트로 제공한다.
- 색상만으로 상태나 카테고리를 구분하지 않는다.
- 관리자 웹은 키보드 조작, 포커스 표시, 대체 텍스트를 지원한다.
- 과도한 전환·깜빡임을 사용하지 않는다.

### 9.7 관측 가능성

- 서버: 요청 오류율, 승인 처리 실패, 편성 생성 실패, 업로드 실패
- 기기: 마지막 heartbeat, 앱 버전, 편성 버전, 마지막 성공 재생
- 경보 제안: 기기 5분 이상 미통신, 15분 이상 편성 갱신 실패, 저장 공간 임계치 도달
- 공개 TV에는 상세 오류 대신 안전한 fallback을 표시한다.

## 10. 운영 정책 초안

### 10.1 승인 기준

- Ziggle 원문과 포스터의 핵심 정보가 일치한다.
- GIST 구성원 대상이며 게시 목적이 명확하다.
- 저작권 또는 개인정보 침해 우려가 없다.
- 이미지가 식별 가능하고 TV 노출에 적합하다.
- 게시 기간이 실제 행사·모집 기간과 맞는다.
- 중복 게시가 아니다.

### 10.2 기간 정책 제안

- 기본 게시 기간: 최대 14일
- 행사 종료 시각 또는 모집 마감 시각을 종료 시각으로 권장
- 종료 시각이 없는 무기한 게시 금지
- 긴급·상시 공지는 관리자가 별도 만료 시각을 지정
- 정책 값은 코드 상수가 아닌 서버 설정으로 관리

### 10.3 콘텐츠 부족 시

우선순위대로 다음을 표시한다.

1. 현재 승인된 포스터
2. 하우스 또는 학교의 상시 안내
3. 전단지 사용법과 QR
4. 현재 시각과 브랜드 화면

생일·졸업 축하 등의 이벤트 콘텐츠는 개인정보와 신청·승인 정책이 정해진 이후 P2로 도입한다.

### 10.4 장애 대응

- 기기 오프라인: 전원, 네트워크, 플레이어 프로세스 순서로 확인
- 미디어 오류: 해당 항목 건너뛰기, 서버에 보고, 관리자에게 경고
- 잘못된 콘텐츠: 관리자 즉시 중단
- Ziggle 장애: 캐시 편성 유지, 신규 신청 일시 중단 안내

## 12. 현재 프론트엔드 프로토타입과의 차이

현재 `flyer-g-fe`는 제품 콘셉트를 보여주는 상호작용 목업이며, 실제 서비스 기능으로 간주하면 안 된다. 경로 분기는 React Router 없이 `window.location.pathname`으로 처리한다.

### 12.1 현재 화면 목업

| 경로 | 역할 | 현재 동작 |
|---|---|---|
| `/` | 대시보드 | 통계, 상태 필터, 승인 대기 목록 |
| `/studio` | 콘텐츠 등록 | 업로드 미리보기, 메타 입력, 게시 토스트 |
| `/display` | TV 미리보기 | 단일/4분할 순환, 일시정지 |

현재 저장소에 보이는 개념:

- 대시보드 통계와 상태별 콘텐츠 필터
- 승인 대기 목록의 단일 승인 동작
- 포스터 업로드와 미리보기
- 제목, 카테고리, 기간, QR 링크 입력
- 단일 포스터 및 4분할 TV 레이아웃
- 5초 자동 순환과 일시정지
- 게시 중, 예약됨, 승인 대기, 종료됨 상태

### 12.2 아직 제품 기능이 아닌 것

- 실제 라우터, 인증, Ziggle API 연동
- 서버 저장, 업로드, 유효성 검사
- 승인·반려·재신청과 상태 전이
- 기간 기반 자동 편성
- 기기 등록, 위치별 편성, kiosk 모드
- 오프라인 캐시, heartbeat, 장애 복구
- 실제 QR 생성과 노출 통계
- 권한·감사 로그·알림

특히 다음 함정에 주의한다.

- 목 데이터의 `published` 또는 `scheduled` 항목을 기간·승인 버전 검증 없이 모두 TV에 표시한다.
- “게시하기”와 “승인하기”는 토스트와 로컬 상태만 바꾸며 새로고침하면 복구된다.
- `QRCodeBox`는 실제 QR이 아니라 시드 기반 패턴이다.
- 목업 `linkUrl`은 `https://ziggle.gist.ac.kr/...` 형태이며, 실제 운영 주소는 `https://ziggle.gistory.me`이다.
- 대시보드의 증감률과 조회수는 하드코딩된 목 값이다.
- `/studio`에서 제목·카테고리를 바꿔도 중앙 포스터 미리보기에는 반영되지 않는다.

### 12.3 의도적으로 축소된 이전 목업 범위

작업 트리에서 제거된 이전 UI는 “포스터 제작 도구” 방향이었으며, 현재 기획은 “완성 포스터 업로드 + 승인 + 노출”로 단순화된 것으로 본다.

- 제거된 예: 디자인 패널, 다중 페이지 관리, 템플릿/요소 사이드바
- 제거된 예: 2분할·8그리드 디스플레이, 조회수 차트, 일정 패널, 제작 가이드 카드

MVP에서는 제작 도구를 다시 넣지 않는다. 필요하면 P2의 템플릿 기능으로만 재검토한다.

## 13. 인수 테스트 시나리오

### AT-01 정상 신청과 예약 게시

```gherkin
Given 로그인한 Ziggle 사용자가 본인의 공지를 작성했고
And 유효한 포스터와 미래의 게시 시작·종료 시각을 입력했을 때
When 디지털 게시판 게시를 신청하고 관리자가 승인하면
Then 신청은 시작 전까지 "예약됨"으로 표시되고
And 시작 시각 이후 대상 디스플레이 편성에 포함되며
And 종료 시각 이후 편성에서 제거된다
```

### AT-02 반려와 재신청

```gherkin
Given 승인 대기 신청이 있을 때
When 관리자가 사유를 입력해 반려하면
Then 게시자는 반려 사유를 확인할 수 있고
When 게시자가 포스터를 수정해 재신청하면
Then 새 검토 회차가 생성되고 이전 이력이 유지된다
```

### AT-03 승인 후 중요 변경

```gherkin
Given 게시 중인 신청이 있을 때
When 게시자가 포스터 이미지 또는 게시 기간을 변경하면
Then 변경 버전은 승인 대기로 전환되고
And 기존 승인 버전의 처리 정책에 따라 유지 또는 중단되며
And 미승인 변경 버전이 TV에 노출되지 않는다
```

### AT-04 오프라인 재생

```gherkin
Given 기기가 유효 편성과 미디어를 캐시했고
When 네트워크가 끊기면
Then 기기는 캐시된 콘텐츠를 계속 재생하고
And 캐시 콘텐츠의 종료 시각이 지나면 해당 콘텐츠를 제거하며
And 네트워크 복구 후 최신 편성을 동기화한다
```

### AT-05 긴급 중단

```gherkin
Given 콘텐츠가 여러 기기에 게시 중일 때
When 관리자가 사유와 함께 즉시 중단하면
Then 콘텐츠는 다음 동기화 주기 안에 모든 유효 편성에서 제거되고
And 관리자, 시각, 사유가 감사 로그에 기록된다
```

### AT-06 손상 미디어 격리

```gherkin
Given 재생 목록의 미디어 하나를 불러올 수 없을 때
When 플레이어가 해당 항목을 렌더링하면
Then 오류 항목을 건너뛰고 나머지 콘텐츠를 계속 재생하며
And 기기 상태 보고에 오류를 포함한다
```

## 17. 완료 정의

기능은 다음 조건을 모두 만족해야 완료로 본다.

- 관련 기능 ID의 인수 조건을 충족한다.
- 정상, 권한 없음, 잘못된 입력, 네트워크 실패 경로가 구현되어 있다.
- API 스키마와 프론트엔드 타입이 일치한다.
- 상태 전이와 기간 계산에 자동화 테스트가 있다.
- 관리자 변경 작업이 감사 로그에 남는다.
- 1920x1080 화면과 Raspberry Pi 대상 브라우저에서 검증했다.
- 접근성 기본 점검과 보안 검토를 통과했다.
- 운영 문서와 장애 fallback이 준비되어 있다.
- 목 데이터나 하드코딩된 현재 시각에 의존하지 않는다.
